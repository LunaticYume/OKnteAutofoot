# 产品化缺口审计（阶段6：只审计，未改任何代码）

视角：一个长期每天挂机使用的普通用户。分级：P0 投入使用前必须 / P1 明显提升长期使用 / P2 以后再做 / WON'T DO 复杂度大于收益。

## 1. 用户输入

| 项 | 现状 | 分级与建议 |
|---|---|---|
| 目标材料数（角色/练度/直接缺口） | ✅ 已有 | — |
| 当前库存 | ✅ 已有，可随时校准 | — |
| 每轮平均掉落 | ✅ 已有（数据表页） | 首次使用必须校准（流程性 P0） |
| 每轮体力 / 每日限额 / reset hour / retry 间隔 | ✅ 已有 | — |
| priority / enabled | ✅ 角色顺序即优先级 + 启用开关 | — |
| **当前游戏内体力** | ❌ 无输入口——planner 只按"每日额度"规划，不感知实时存量，体力不足要等 ok-nte 启动后才发现 | **P1**（配合体力恢复模型，见下） |
| 体力自然恢复参数（上限/速率/钻买次数） | ❌ 未建模 | **P1**（用户已点名"体力恢复预测"） |
| 可自动读取项 | 今日已耗体力（OCR 日志✅）、版本/兼容（✅）、追猎状态（部分） | 已覆盖 |
| 背包库存自动 OCR | ❌ | **P2**（侵入截图识别，价值/成本比一般；先靠手动校准+掉落闭环） |
| 读游戏内存 | — | **WON'T DO**（违背本工具"不改游戏、不读内存"的边界） |

## 2. 计划可理解性

今天刷什么/为什么/还差多少/刷几轮/消耗多少：✅（步骤 reason + 计划 detail，UI 只展示不重算）；为什么在等/下次重试何时：✅（waiting 原因 + 倒计时）；额度构成（限额−已耗−追猎预留）：✅；**下一个目标**：部分（计划表顺序可见，但"达标后明天会刷什么"不可见）；**未来 1–3 天预览**：❌ → **P1**（依赖体力恢复模型；确定性做法：注入 now 纯函数推演，复用现有 planner）。

## 3. 操作安全

Dry Run ✅、三态兼容指纹 ✅、停止 ✅、写前自动备份（保留 20 份）✅、崩溃对账 ✅、异常原因可见 ✅、执行日志 ✅。缺口：**备份无一键回滚入口**（文件在 data/backups/ 但只能手动复制）→ **P1**。

## 4. 历史

已有：day/time/材料/轮数/体力/预计产出/状态/备注，500 条上限，对账零值审计留痕。缺口：duration、exit_code（runtime 里有但历史没有）、**用户确认的实际掉落** → 汇总历史形成 planned vs actual 是**长期最重要**的闭环（自动校准产量的数据来源）→ **P1**；图表可视化 → P2。

## 5. Material 数据维护

静态数据（materials/yields/requirements.json）与用户状态（state.json：库存/目标/启用/优先级）**已分离**，表升级不会覆盖用户数据 ✅（含 version 字段）。缺口：**自身数据格式的 schema version 与导入导出**（换机/备份/未来字段演进）→ **P1**；多来源材料（同一材料多个副本，按单位体力产出排序）：模型字段可表达、未启用 → **P2**（明确禁止复杂优化器，保持确定性启发式）。

## 6. Upstream Update Assistant

顶栏实时指纹标签（三态+悬停原因）+ 预演按钮已等价于"检查兼容性"；独立按钮价值小 → P2（可选：一键生成兼容报告文本，把 UPSTREAM_COMPATIBILITY 清单与当前实测值拼成可分享的报告）。

## 汇总

- **P0（代码层无缺口）**：剩余 P0 是动作而非代码——①完成 E2E 报告 Manual PASS 三项（真机预演→实跑一次核对"双倍/单倍"记账；真机更新演练；真实体力不足场景）；②首次使用前校准产量表。
- **P1（建议下一批，按序）**：1) 实际掉落校准闭环（历史确认 → 更新 yields）；2) 体力恢复模型 + 当前体力输入 + 未来 1–3 天预览；3) 配置导入导出 + schema version；4) 备份一键回滚。
- **P2**：历史增强（duration/exit_code/图表）、多来源材料、兼容报告一键生成、背包 OCR。
- **WON'T DO**：读游戏内存/注入、复杂优化器、多账号并行（违反"单循环单实例"核心契约）。
