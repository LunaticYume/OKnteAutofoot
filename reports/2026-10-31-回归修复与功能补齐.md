## 第七轮：背包 OCR v3——窗口绑定重做与点击遍历（2026-11-03 追加，经 workflow 编排实施）

### 实测三问题的根因（取证）

## 第八轮（紧急）：EXE 无法启动——Windows 端口排除区（2026-11-03）

**现象**：新 EXE 打开后访问失败；之后每次启动立即退出。crash.log 实锤：`RuntimeError: 端口 8766~8786 均无法绑定（[WinError 10013] 访问权限不允许…）`。

**根因（两条叠加，均已实证）**：
1. **Windows 动态端口排除区**：`netsh interface ipv4 show excludedportrange protocol=tcp` 实测 **8766~8865 整段被排除**（Hyper-V/WSL/NAT 类组件重启后随机保留端口段的常见现象——10-31 之前不存在，某次重启后出现）。面板的自动避让只试 8766~8786，整段恰在排除区内 → 全部 10013 → 无法启动。排除区是**机器状态**，随时可能再变。
2. **主端口 8765 被抢占**：`baidupinyin.exe`（百度输入法，PID 20136）正在监听 0.0.0.0:8765——输入法会随机抓临时端口。旧实现避让+1..+20 全在排除区内，无路可走。

**修复（app/main.py create_server 重写 + `_port_candidates` 纯函数）**：
- 候选序列扩为 相邻段 [P, P+20] + **跳段 [+100, +120] 与 [+200, +220]**——10013（排除区）时大步跳出排除区；
- 10013 与普通占用分流：报错信息给出两个可操作解法（管理员 `net stop winnat && net start winnat` 清动态排除区 / 改 data/state.json 的 port 并用 netsh 查看排除区）；
- selftest 改写：候选序列断言（8765 基准 → 含 8865/8965 跳段）、monkeypatch 全候选被占、10013 形态报错断言。**74/74** 全绿（含工作流新增的 OCR v3 用例）。

**已为你做的即时恢复**：`dist/OKntePlanner_single/data/state.json` 与 `dist/OKntePlanner/data/state.json` 的 port 已改为 **9871**（实测可绑、不在任何排除区）——现在双击 EXE 即可启动；之后每次启动若 9871 再被占，新的跳段避让会自动找可用端口。

**长期建议**：8765/8766 段从此不要再依赖——新版面板会自动跳段，无需手动干预；若想根治排除区，管理员执行一次 `net stop winnat && net start winnat` 即可清掉（不影响 Hyper-V 功能，但下次重启可能再出现）。

### 两版 EXE 的区别（用户疑问）
- **OKntePlanner（启动器版）**：`异环养成规划器.exe` 是 C# 小引导器——找 Python（exe旁 python\ → ok-nte 内嵌 python → PATH）后以 `python -m app.main` 运行**旁边的 app/ 源码目录**；数据在 `dist/OKntePlanner/data/`。优点：热修后直接复制 app/ 即生效；缺点：依赖 ok-nte 的 Python 路径存在。
- **OKntePlanner_single（单文件版）**：PyInstaller 把全部代码打成一个 `OKntePlanner.exe`，**自包含、不依赖任何 Python 安装**；数据在 EXE 旁 `data/`。你日常用这个。
- 两版数据目录互相独立——换版后"看起来数据丢了/打不开"实为空库冷启动。
- 本轮后两版均为最新代码（launcher dist app/main.py md5 与源码一致已核验）。
